# V4 开发指南

> 2026-11-05。本文整理当前对 V4 的讨论，供交互设计与后续开发使用。它不是已完成清单。凡标为“建议”或“待验证”的内容，应由原型体验、技术验证和律师评测决定是否采用。

## 1. 目标与已确认的边界

V4 的目标是一个以 Agent 为基础的法律工作系统：能持续办理复杂任务，形成专业、可审阅的判断和文书，并承担律师助理常做的材料整理、检索、起草与办案跟进工作。律师应能随时追问、纠正方向、修改成果和决定关键事项。

1. **独立设计 V4。** 不主动查阅、沿用或复制 V3 的产品和代码；只有用户明确要求查看 V3 时才查看。
2. **先做 interactive design。** 先让用户体验可点击的 V4 原型并做产品决策，再实施相应功能。
3. **按 bullet 开发，并采用 Agile 与 CI/CD。** 一个 bullet 是一条能从用户操作走到可查看成果的完整小流程；通过验收和回归后再推进下一条。迭代节奏、自动检查和发布规则见第 7 节。
4. **区分两种 Skill。** 法律 Skill 是产品运行时的专业流程；开发 Skill 是指导工程实现、测试和发布的工作规范。
5. **首版只开发网页端。** 桌面宽屏和手机浏览器都需可用；独立安装的电脑端与原生手机端保留架构方案，待网页端的核心流程验证后再决定开发。

## 2. 产品架构方向（建议）

律师提出目标 → Agent 在当前工作空间规划并调用工具 → 按需加载法律 Skill → 读取案件材料与法律来源 → 生成可追溯成果 → 程序校验 → 律师审阅与修改 → 留下版本和运行记录。

- **工作空间：**工作台处理跨案事务；打开案件后，任务、上下文和可用工具限定在该案。案件数据保持隔离。
- **Agent harness：**负责多轮工具调用、任务状态、断点恢复、上下文管理、权限、失败处理、成本预算和运行轨迹。关键的法律权限、审计、工具协议与专业流程由项目掌控；LangGraph 是否用于底层状态编排，先用一条任务流验证再决定。实际完成质量需要靠模型、工具和评测验证，不能预先承诺与其他产品相当。
- **模型接入：**即使不采用现成 Agent API/SDK，仍需模型推理能力。使用远程模型接口还是本地模型尚未决定；“完全不用任何推理 API”意味着需要本地推理方案。
- **专业工作底稿：**把材料、证据、事实、争点、法律依据、结论与文书段落关联起来。每项重要事实和依据应可返回原始位置，并能显示冲突或缺口。
- **律师控制：**关键策略、外发成果和高影响操作有明确的审阅点；律师的修改应保留版本，并用于改进 Skill 和评测。

多轮任务的 token 预算可暂按同任务单轮的 **3–6 倍**预留。这只是规划估算，不是产品指标。实现时逐次记录输入、输出、缓存命中、耗时和任务结果，再用同一批任务实测成本与收益。

**竞争方向：**保持 Agent 式的自然语言、多轮和工具执行体验；把长期案件工作空间、事实与证据可追溯、律师审定的法律 Skill／文书库、专业评测和纠错积累做成产品核心。不以侧栏功能数量或通用工具连接数量作为竞争目标。以上是产品假设，须由用户体验与同任务对比验证。

### 技术栈与多端顺序

- **当前开发范围：**Next.js＋TypeScript 网页端；同时设计桌面宽屏与手机浏览器布局。TypeScript 主后端独立承担案件、身份权限、材料、文书和任务接口；[Next.js 页面接口](https://nextjs.org/docs/app/guides/backend-for-frontend)只处理页面需要的轻量服务。OCR、索引和长时间 Agent 任务放后台 worker。
- **桌面安装版（后续）：**在网页端稳定后评估 Electron 或 Tauri。[Tauri 与 Next.js 的组合](https://v2.tauri.app/start/frontend/nextjs/)需要静态导出，不能假设网页的服务端功能可原样打包；是否需要本地文件、离线或系统集成能力，再决定方案。
- **原生手机端（后续）：**如手机浏览器不能满足拍照上传、通知、文件处理等真实任务，再评估 [Expo／React Native](https://docs.expo.dev/router/introduction/)。复用 API 契约、业务类型和规则，移动界面按手机任务单独设计。
- **Agent 实现：**若接受引入框架，可先评估 [LangGraph 的 JavaScript／TypeScript 版本](https://docs.langchain.com/oss/javascript/langgraph/thinking-in-langgraph)，不必仅为此增加 Python。Python 只在 OCR、文档处理或模型工具有明确性能或生态优势时，作为独立 worker 加入，并通过版本化接口与 TypeScript 后端通信。

### 数据与模块边界

- **主数据库：PostgreSQL。**保存用户、组织、案件、材料元数据、证据关系、任务状态、文书版本和审计记录。原始文件放对象存储，数据库记录文件标识和关联；所有案件查询由应用层校验权限，必要时再用 [PostgreSQL 行级安全](https://www.postgresql.org/docs/current/ddl-rowsecurity.html)作为第二道约束。
- **检索与队列按需求增加：**初期可评估 PostgreSQL 全文检索与 pgvector；法条、案号等精确检索和语义检索都要用律师标注样本衡量。只有当数据量和质量评测证明有必要时才引入 OpenSearch。Redis 可在任务队列或缓存确有需要时加入，不能作为案件事实的主存储。
- **模块化单体：**首版保持一个主要代码库和可统一部署的后端，按身份权限、案件材料、阅卷证据、法律研究、文书、合同和 Agent 执行划分模块。每个模块拥有自己的接口、数据表、迁移、测试及负责的前端功能；禁止跨模块调用内部实现或直接改写对方数据。跨模块协作通过公开接口或明确的事件进行。
- **可拆卸的范围：**可选功能以独立入口、权限、工具／Skill、数据迁移、测试和评测组成；能独立启停和更新。用户身份、案件归属、权限及来源追溯是共享底座，依赖关系必须明确，不把它们当作可随意移除的插件。

### 用户注册与测试账号

V4 应有用户体系。首批真实使用建议采用**邀请注册**：管理员邀请 → 用户验证邮箱并设置登录方式 → 登录进入所属组织与案件 → 按角色和案件授权使用功能。包含退出登录、找回账号／重置凭据、会话失效和基本操作审计；公开自助注册待产品开放范围确定后再评估。身份认证应采用成熟方案，按 [OWASP 身份认证](https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html)与[会话管理](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet)要求实现，不自行发明密码或会话机制。

开发与测试环境各准备**一个主要的可重建测试账号**及合成案件，用种子脚本创建；跨用户权限测试临时创建受限账号。账号凭据通过环境密钥配置，不写入代码、指南或共享截图。自动化测试覆盖注册、登录、退出、越权访问和跨案隔离。生产环境不自动创建默认测试账号，也不放入真实客户材料。

## 3. 八条产品开发线（规划目录）

前四条：

1. **Agent harness：**工作台与案件任务、多步执行、状态恢复、工具协议和运行记录。
2. **案件与材料：**案件空间、文件接入、解析与 OCR、原件定位、权限和版本。
3. **阅卷与证据：**跨文档阅读、事实时间线、证据目录、证明关系、矛盾与待补事项；专项阅卷加载特定业务规则。
4. **法律研究：**法律来源、法律咨询、类案检索、案例比较、事实与规则的匹配及论证。

后四条：

5. **文书生产：**法律 Skill、文书库、要素式起草、诉讼文书、法律意见与深度报告。
6. **合同与合规：**合同起草，自由、模板、补充协议、主体及比对审查，制度审查与法治体检。
7. **成套交付：**把阅卷、研究、起草和校验组合为一个任务，例如起诉状＋证据清单、一审判决上诉分析、对手抗辩预判，以及保全或执行材料。
8. **办案运营：**待办、节点、汇报、结案、归档和按实际任务接入的外部工具。

这八条是产品能力归类，**不是八个同时启动的项目**。专业质量、案件隔离、安全、评测和律师审阅贯穿每一条。

**优先顺序：**首批验证阅卷与证据、法律研究、文书生产及一项成套交付，先形成完整办案成果；合同与合规的扩展按目标律师群和原型反馈决定。待办与案件管理保留完成首批任务所需的最小能力，广泛外部连接后置。

### 对外部产品功能的取舍

- 法律咨询的多个版本先归为同一能力的“快速／深入”等模式；不为版本名称分别建设系统。
- 类案检索的六种问法归入统一检索能力，按案号、案情、焦点、裁判口径、多维条件或罪名选择检索方式。
- 法律阅卷、证据阅卷、专项阅卷共用材料与事实证据底座，再加载各自的专业流程。
- 各类法律数据库作为有权限和出处记录的数据来源；不以自建十个数据库作为 V4 的前置条件。
- 通用邮箱、网盘、会议等连接按真实办案任务加入；“Claw”对应 Agent 的工作方式与成套交付能力，不另做一个同名菜单。

## 4. 法律 Skill 与文书库

一个文书 Skill 负责一类明确任务的**完整工作流程**，文书库保存经审核的模板、写作规则、参考样稿和版本。Skill 指引 Agent 何时、按什么条件从文书库取内容；工具负责检索、读取、生成文件和程序校验。取回的样稿用于参考，文书中的事实与判断必须针对本案重新形成。

以“民事起诉状 Skill”为例：确认适用范围 → 读取案件底稿 → 检查当事人、诉请、事实、证据与依据是否齐备 → 标出缺口并取得必要决策 → 检索及核验依据 → 选择模板起草 → 检查事实、金额、日期、诉请和引用的一致性 → 交律师修改 → 留存版本。其他文书可复用底座，但应有各自的流程和专业检查。

每个法律 Skill 至少说明触发条件、输入要求、流程、可用工具、停止或提请律师的条件、输出结构、校验规则、适用范围、版本和评测样本。文书库的模板与样稿需区分管理。法律 Skill 的专业内容应由执业律师审定。

## 5. 先做交互原型，由用户决定

原型阶段先画全局任务地图，再制作三条可点击任务流：

1. 上传一案材料 → 阅卷并查看事实和证据 → 生成、修改起诉状与证据清单。
2. 提出法律问题 → 检索与比较类案 → 查看依据和判断。
3. 提交一份合同 → 审查条款 → 查看修改建议与可交付成果。

原型使用模拟案件和模拟 Agent 结果。除了顺利完成，还应能体验缺材料、证据冲突、引用未核实、执行失败和任务恢复。登录／邀请注册入口也做可点击示意。重点让用户决定入口、页面布局、Agent 进度、接管或确认时机、出处展示及成果编辑方式。

每条任务流由用户实际点击体验，并记录**保留／修改／删除**及原因。无需在开工前画完所有功能：先确定整体交互原则和关键流程；以后每个功能 bullet 开发前，再做相应原型。原型验证使用方式，不能证明模型的法律判断质量；后者需另做技术验证和律师评测。原型代码不能直接当作生产实现。

## 6. Bullet 开发与工程验收

每个 bullet 写清：目标用户、输入、可见操作、预期成果、异常情形、留存的数据、专业质量要求和验收样例。一个完整 bullet 依次通过以下五关：

1. **定义：**给出真实任务样例、成功标准和不应发生的错误。
2. **设计：**明确数据、接口、工具权限、来源追溯、迁移及回退方式。
3. **实现与重构：**完成前后端闭环；整理本次触及的重复或混杂代码，保持已验证的行为。
4. **验证：**自动化测试、用户操作回归、律师样本评测及成本和耗时记录。
5. **审查与交付：**审查差异、安全和数据影响；确认可恢复、可回滚，再记录结果并进入下一 bullet。

原型决定之后，先建最小技术基础：网页壳、邀请注册／登录、测试账号、案件隔离、PostgreSQL、对象存储和本地自动检查。基础本身要有验收测试，但不扩展为庞大的平台工程。第一条建议实现的**法律业务** bullet 当前候选是：“上传两份材料，生成每项都可点回原文的事实时间线。”随后再扩展证据目录、法律研究和“起诉状＋证据清单”成套交付。

## 7. Agile 迭代与 CI/CD 交付流程

**总体原则：**用短迭代验证用户价值，用自动化持续确认工程质量与法律质量。一个迭代以一条主要 bullet 为交付目标；原型阶段验证交互，进入真实开发后再用法律评测验证专业能力。先在本地形成稳定的自动检查与交付习惯；需要远程协作和线上试用时，再接入远程 CI/CD。

**一句话流程：**用户在本地体验可点击原型并定方向 → 建最小网页和账号基础 → 每次完成一条可用的法律业务流程 → 本地自动测试 → 用户与律师验收 → 需要线上试用时再部署 → 根据反馈继续下一条。

### 本地优先，按需远程发布

- **原型和首批开发：**在本机运行网页及测试数据，用户直接在本机浏览器验收。每次改动先运行本地构建、测试与法律样本评测。建议给新的 V4 代码库建立本地 Git 历史以便回退；这不要求上传 GitHub。
- **远程仓库：**GitHub 用于远程保存代码、协作审查和触发 GitHub Actions；它本身不是对用户开放的网站。只有需要多人协作、异地备份或远程自动检查时，再决定是否建立私有仓库及推送节奏。
- **线上试用／正式发布：**等本地流程稳定、确需让外部用户访问时，再选择服务器与部署平台，配置测试环境、访问控制和发布检查。代码是否托管在 GitHub 与网站是否上线，是两个独立决定。

### 7.1 迭代节奏与决策

1. **维护任务清单：**按真实律师任务排序，每项记录用户场景、输入、可见成果、异常情况、法律风险、验收样例和待定决策。
2. **短周期交付：**初期建议每 1–2 周评审一次；每次选一条主要端到端 bullet，控制同时在做的功能数量。周期是工作节奏，不要求未达标功能按日历强行上线。
3. **开工前确认：**用户体验可点击原型并决定保留／修改／删除；开发者与律师把成功条件、专业红线和测试样本写进任务卡。
4. **迭代末验收：**展示实际可操作流程、测试与法律评测结果、失败样本、耗时和成本；用户决定接受、修改或调整下一项优先级。
5. **复盘：**记录影响交付的返工、错误与等待原因，更新下一轮任务和工程规则。不要以完成页面数量或代码行数衡量进度。

### 7.2 持续集成（CI）

本地开发阶段把以下检查做成一条可重复运行的命令，每次完成 bullet 前执行。接入远程仓库后，在每次合并请求自动执行相同检查；届时再设置受保护主分支与代码审查。建议检查顺序：

1. **快速检查：**依赖锁定、格式、静态检查、类型检查、构建；失败立即反馈。
2. **行为测试：**关键业务单元测试、接口契约与数据库集成测试；重点覆盖案件隔离、权限、任务状态恢复和文书数据一致性。
3. **流程测试：**用模拟案件跑关键浏览器端到端流程，包括成功、缺材料、冲突、工具失败、律师修改及恢复。只把稳定、关键的流程设为交付必过项；接入远程仓库后再设为合并必过项。
4. **安全检查：**依赖风险、密钥泄漏、代码安全扫描与敏感日志检查；高风险问题阻断交付，处理标准参考 OWASP ASVS，并结合实际部署形态选择适用项。
5. **法律回归评测：**对模型、提示词、Skill、文书库、检索或工具变更运行对应的固定脱敏样本；检查出处真实性与定位、法条及案例适用性、事实遗漏、证据矛盾、文书要件和结论依据。高风险错误阻断交付或发布；较大规模的评测可安排在发布前运行。

评测集要版本化，包含预期结果、律师评分规则和典型失败样本。通过阈值按任务与风险事先设定，不能用“模型回答流畅”替代专业验收。新发现的专业错误应先加入回归样本，再修复。

### 7.3 持续交付与发布（CD）

1. **本地交付：**先在本机运行最新版本与合成案件，完成自动检查、用户交互验收和律师专业验收；把可运行版本、测试结果和问题记录下来。此阶段不需要线上部署。
2. **测试环境与生产发布：**需要远程试用时，才自动构建并部署到受控测试环境，运行冒烟测试。正式上线初期由负责人核对改动、专业评测、数据迁移和回滚方案后批准；生产自动部署留到后续成熟阶段。
3. **版本记录：**同一发布记录代码、模型、提示词、法律 Skill、文书模板、检索配置、数据库迁移和评测集版本，保证问题可复现。
4. **逐步放量与回滚：**新能力可先限测试用户或部分案件；监控异常后关闭功能或恢复上个可用版本。数据库迁移需兼容回退或有已验证的恢复办法。
5. **上线监控：**观察任务完成率、专业错误、无出处结论、律师修改量、工具失败、延迟、token／成本及安全事件；出现严重法律错误、跨案数据泄露或无法恢复的任务失败时停止放量并处理。

**第一阶段的最低可执行版本：**本地原型评审记录 → 一条 bullet 的验收任务卡 → 本地一键构建、关键测试及法律样本评测 → 本地运行供用户与律师验收 → 保存可恢复的版本。需要远程试用时，再增加私有远程仓库、远程 CI、受控测试环境、人工批准生产发布、监控和回滚演练。

## 9. 必守的质量与风险规则

- **测试按行为和风险设计：**关键业务单元有单元测试；跨模块状态、权限和数据库操作有集成测试；律师实际任务有端到端验收；法律输出另有律师评测。不要为每个简单函数凑一条复制实现的测试。
- **法律结论可核对：**记录事实与证据的对应、法条及案例的原始出处、检索时间、适用范围和未解决的争议；不能把“查到同名条文”当作论证正确。
- **控制 Agent 权限：**工具只接触当前授权范围；文件、网页、检索结果和参考样稿是数据，不可让其文字成为新的系统指令。重要写入及对外成果应有明确审核点。
- **保护案件资料：**权限隔离、密钥管理、日志脱敏、备份恢复、导出控制和版本回退要在相应 bullet 中验证。
- **持续量化：**记录任务完成率、专业错误、出处可追溯情况、律师修改量、工具失败、耗时与 token／成本。用固定样本比较每次模型、Skill、工具或提示词改动。
